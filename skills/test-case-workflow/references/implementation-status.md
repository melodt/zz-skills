# Implementation status write-back

Before reporting the outcome or performing a final commit, identify the existing spec, ticket list or ticket files, and test-case documents used by this task. Update each applicable writable local document automatically with the observed implementation and verification status for the affected scope, including partial or blocked work. Preserve unrelated content, other people's edits, and history. Do not create missing source documents just to record status; report missing or inaccessible sources and any write-back failure in the final response.

- **Spec:** record affected requirements, implemented versus remaining scope, verification outcome and evidence or case-document pointer. Mark the whole spec complete only when its full scope and required verification are complete; a single ticket or a narrowed verification scope is insufficient.
- **Tickets:** update only the affected ticket's existing status and acceptance checkboxes in line with actual implementation and required verification. Record blockers and evidence; leave unchecked anything incomplete or unverified. Preserve dependency information and other tickets. Do not close a ticket whose applicable completion gate has not passed.
- **Detailed design:** use it as an implementation and acceptance input, not a task-progress record. Report deviations and pending decisions in the task or spec and final response; do not add implementation or verification progress to the design. Do not change design content or approval status merely to match implementation; update design decisions only when explicitly requested or confirmed.
- **Test cases:** update existing applicable case results and evidence honestly, including unexecuted, failed, blocked and stale cases. When `test-case-workflow` applies, use its detailed execution and completion rules. Ordinary implementation skills do not create a case document solely because of this instruction.

Use an existing progress or status convention when it distinguishes implementation, verification, and approval; otherwise add a concise, dated implementation progress section or fields, including scope, outcome, evidence, blockers and remaining work. Record the actual checked revision or identifiable working-tree state, without inventing a future commit hash. A partial or failed run must never be recorded as complete. If changes after verification affect the evidence, revise the status and rerun affected checks as required.

External tracker updates, issue closure, and other external writes require the applicable user authorization and tracker workflow. If unavailable or unauthorized, record what is possible locally and report the missing external update; do not claim synchronization. Before declaring the task complete, check that all required and authorized write-backs succeeded; if one cannot be performed, report the affected document and treat the write-back as incomplete. Include relevant local status updates in any authorized task commit, and never perform a final completion action before applicable validation gates pass.

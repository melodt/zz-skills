# Code Skeleton

依据详细设计和正式测试用例文档，将范围内每项已确认的设计及用例转成可追踪、可继续实现的代码骨架，并结合可用 spec 和 tickets 核对来源。默认先做 `plan`，只有用户明确要求执行或指定 `--apply` 才将骨架写入工作区。自然语言与 `--spec`、`--design`、`--tickets`、`--ticket`、`--plan`、`--dry-run`、`--apply`、`--verify` 均按相同流程解释；这些是对话参数，不代表提供了 CLI。

## 运行顺序

1. 读取适用的 `AGENTS.md`、用户指定文档、仓库配置和相关代码；记录所有输入的路径及版本或哈希。详细设计和对应功能的正式测试用例文档是必需输入；未指定时按项目约定查找，候选不唯一或缺失时报告并请求定位。任一必需文档缺失、不可读或无法确定归属时，记录阻塞并停止受影响范围的骨架规划和生成；不凭空补写设计或用例。优先使用 CodeGraph / codebase-memory-mcp 理解符号关系；图谱不可用时读取具体文件。
2. 逐项核对详细设计的范围、覆盖清单、能力、规则、状态、数据、接口、异常、权限和验收，与用例的来源、前置条件、步骤、数据及预期；不适用项保留原因。用户指令优先，现有代码约定只补充未规定的实现细节。文档之间或与用户指令存在实质冲突时，列明双方依据和影响，标记待确认并阻塞受影响项；不按文档类型静默裁决，不改变设计或用例以适配代码。
3. 确定范围：用户指定 ticket 时只处理这些 ticket；未指定时先列出发现到的未完成 ticket，等待范围明确。记录范围内与跨 ticket 相关的设计和用例，以及范围外条目；按依赖做拓扑排序。
4. 按 [计划模板](references/plan-template.md) 建立逐项追踪矩阵：来源/设计及验收编号 → ticket → 用例 ID 及预期 → 模块/接口/文件 → 骨架或测试占位 → 验证与结果。每项范围内设计和每条适用用例，包括设计中没有用例的条目和跨 ticket 场景，都须有映射，或有明确的缺口、原因和阻塞状态；优先级不豁免覆盖。缺少用例、设计依据、公共契约或存在循环依赖时阻塞受影响项，不猜测；继续不受影响的工作。
5. 生成或更新 `docs/implementation-plan.md`，记录输入哈希、目标文件、接口、依赖、占位点、验证命令、风险和状态。计划格式见 [references/plan-template.md](references/plan-template.md)。
6. 在 `plan` 模式只生成或更新计划并展示预期 diff、冲突和阻塞项，不写代码或测试执行结果。`apply` 模式按 ticket 处理：公共接口与类型 → 模块边界 → 适配器和依赖 → 最小实现 → 明确支持的入口注册 → 测试骨架。每个接口、类型、字段、状态和分支都必须符合已确认设计及对应用例；不能完整实现的行为明确标记占位和剩余工作，不用虚假的成功结果、跳过的分支或空断言冒充实现。若输入在应用前变化，重新核对追踪矩阵并重新计划。
7. 每个 ticket 先生成到临时位置并做语法级检查，再应用到工作区。记录应用前内容和哈希，仅恢复本 ticket 实际写入且未被其他人改动的内容；无法安全恢复时停止并报告。保护人工修改；无法可靠合并时跳过并报告。失败时保留前面已验证的结果。
8. 使用 `TODO(ticket:<id>, kind:<category>): <remaining work>` 标记未完成工作。`kind` 使用 `business-logic`、`integration`、`validation`、`design-gap` 或 `manual-decision`。
9. 从仓库真实配置识别验证命令，按 `syntax`、`unit`、`build`、`integration` 分层执行。对照追踪矩阵检查每项生成内容是否与已确认设计和用例一致，记录证据、未实现项与验证缺口。外部服务不可用时按适用情况使用本地替身，并明确未执行的集成验证；替身、编译成功或测试占位不代表完整功能用例通过。真实执行用例时按 [test-case-workflow](../test-case-workflow/SKILL.md) 记录实际结果与证据；该依赖不可用时报告并停止相关用例状态回写，不伪造通过。变更使已有通过证据失效时按其规则标记需复验，保留历史。
10. 更新 `.code-skeleton/manifest.json` 和 `.code-skeleton/runs/<run_id>.json`，输出 Markdown 报告与 JSON 结果。报告每条设计和用例映射、实际检查结果、未实现占位、阻塞及范围外项；分别报告骨架状态和功能用例状态。恢复前核对输入哈希和文件现状，变更时重新计划；不静默覆盖历史记录。报告格式见 [references/report-template.md](references/report-template.md)。

## 约束

- 默认只修改当前 ticket 及直接支撑文件；跨模块重构必须单独列出并解释。
- 不自动引入新框架、访问真实外部系统、读取或生成真实凭据、执行真实迁移、commit、push、建分支或关闭 ticket。
- 数据库、消息队列和第三方 API 只生成接口、模型、迁移草稿、mock、本地替身和配置样例。
- 路由、容器、插件或 CLI 注册只有在详细设计或现有注册模式明确支持时才自动修改。
- CI 只允许 `plan` 和 `verify`，不自动 `apply`；存在未映射需求、未解析变量或阻塞项时报告非成功状态。仅在实际存在命令行集成时返回非零退出码。
- 计划、日志和报告不得记录密钥、令牌、连接串或不必要的个人信息。外部 ticket 状态只按已有约定和用户授权更新，不自动关闭。
- 骨架成功条件是：范围内每项适用设计及每条用例均有有效映射并与已确认契约一致、没有未解决的覆盖缺口或阻塞，必要骨架检查通过，结果已归档且 diff 可解释；否则报告 `partial`、`blocked` 或 `failed`。占位和未完成的业务逻辑须明确列出，骨架成功不等于功能完成、ticket 完成或用例通过。
- 功能验证只有在相关用例实际执行并符合全部预期、具有有效证据时才能标记通过。仅当批准范围的全部适用用例通过才可宣称该范围验证完成；用户明确缩小范围时记录排除项，不声称原范围通过。详细设计不记录任务进度。

## 持久化产物

- `docs/implementation-plan.md`：计划、追踪矩阵和运行历史。
- `.code-skeleton/manifest.json`：文件、ticket、输入哈希、skill 版本、生成时间和状态。
- `.code-skeleton/runs/<run_id>.json`：单次运行的结构化结果。
- `.code-skeleton/tmp/`：成功后清理，失败时保留诊断产物。

配置规则和字段见 [references/configuration.md](references/configuration.md)。验证和错误分类见 [references/verification.md](references/verification.md)。

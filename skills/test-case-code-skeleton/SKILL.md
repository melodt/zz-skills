# 测试用例驱动的代码骨架

使用同级 [code-skeleton](../code-skeleton/SKILL.md) 的骨架流程和同级 [test-case-workflow](../test-case-workflow/SKILL.md) 的用例、证据及状态规则。安装时保留三个目录的相邻结构；任一依赖不可用时报告并停止，不声称已完成对应工作。读取原 skill 引用的相关模板、配置和验证说明。本文对用例追踪、冲突和完成状态的要求补充原骨架流程；用户指令及适用仓库规则优先。

## 输入与范围

1. 读取用户指定的测试用例文档、spec、tickets、详细设计及适用项目指令；记录来源、版本或哈希和不可读取项。未指定用例路径时，依据用户提供的功能及现有文档约定查找对应文档；有多个候选且不能可靠确定时列出候选并请求明确。必须读取到对应功能的正式用例文档，才能计划或生成该功能的测试用例驱动骨架；缺失、不可读或身份不明时报告阻塞，不自行虚构用例。用户另行要求生成用例时，按 test-case-workflow 处理，并保持生成用例与授权写入骨架的动作分开。
2. 保留原 skill 的范围选择和默认 plan 行为：只处理用户指定的 ticket；未指定时列出发现的未完成 ticket，等待范围明确。默认只规划；仅用户明确要求执行或指定 `--apply` 才按原流程写入骨架。`--verify` 按原流程验证已有骨架，不等于授权实现业务。
3. 读取所选 ticket 和跨 ticket 相关用例的编号、来源、前置条件、数据、步骤、预期、状态和覆盖缺口。按来源核对用例与 spec、ticket 及详细设计；用例约束不得被静默忽略或改写。若用例、来源或用户要求冲突，列出双方及影响，标记受影响部分待确认并阻塞其骨架生成，继续不受影响的部分；不因原骨架 skill 的文档优先顺序自动裁定业务冲突。缺失或不完整的预期、公开契约、依赖和用例映射也要明确记录并阻塞受影响部分，不猜测业务规则。

## 追踪与生成

4. 在原计划和报告中扩展追踪矩阵：`来源/验收标准 → ticket → 用例 ID → 场景及预期 → 模块/接口/目标文件 → 骨架或测试占位 → 验证及结果`。每条当前范围内的适用用例，包括正常、边界、异常、权限、状态和跨 ticket 场景中实际适用的条目，都必须对应结构、测试占位或有依据的待确认／阻塞说明；用例优先级不豁免覆盖。区分未纳入当前范围的用例，不把它们标成已覆盖。
5. 先按原流程检查依赖、文件边界和接口，再在 `apply` 中按 ticket 生成代码骨架和适用的测试骨架。接口、输入输出、校验与错误分支必须能支撑各用例的已确认前置条件和可观察预期；占位不伪装为业务实现。将用例 ID 与相关骨架或测试位置关联，明确剩余业务逻辑、集成和验证；保持原 skill 的 TODO 格式、注册限制及外部系统约束。不要为让构建通过而编造成功返回、忽略错误或制造无断言的假通过测试。
6. 沿用原 skill 的计划、临时检查、保护已有修改、分层验证、manifest 和运行报告规则；在计划和报告中记录用例文档版本、用例映射、实际执行的命令和各用例的执行结果。若用例文档或其他输入在应用前变化，重新核对映射并按原流程重新计划。`plan` 仅形成计划及预期 diff；不写代码或伪造执行记录。

## 验证与交付

7. 运行仓库实际支持且任务要求的骨架语法、构建和其他适用检查，报告真实结果。只有实际执行且满足完整前置条件、步骤和预期，并按 test-case-workflow 留有有效证据的用例，才能更新为通过；测试占位、mock、编译成功或计划覆盖本身都不能证明功能用例通过。未运行的保留未执行，执行受阻、结果不符或预期不明时按共享规则分别标记，先前证据因变更失效时标记需复验。保护已有用例历史；仅在实际执行或确认原证据失效时更新对应记录。
8. 报告当前范围、每个用例的映射和实际状态、覆盖缺口、阻塞、剩余实现及验证证据。骨架状态与功能验收状态分别报告：仅当目标范围内每条适用用例均有有效映射、无未解决阻塞且原 skill 的骨架检查满足时，才能称骨架完成；功能或 ticket 的验证完成必须满足 test-case-workflow 对全部适用用例实际通过的门槛。用户明确缩小验证范围时，记录并单独报告排除项，不能宣称原范围通过。阻塞或未完成时报告 `partial`、`blocked` 或 `failed`，不关闭 ticket。

遵循原 skill 对数据、外部系统、凭据及 Git 操作的限制；生成骨架不授权提交、发布或关闭工单。详细设计作为设计输入，不写入任务进度；如实在适用的计划、报告或 ticket 中记录差异。

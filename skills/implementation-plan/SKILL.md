# 实施计划

把已有需求、任务和设计转成可供实现者执行和验证的计划。默认只交付计划文档；写计划不代表开始编码、执行迁移或发布任务。

## 读取与核对

读取用户指定的 spec、全部相关 tickets、详细设计及其更新，遵循仓库约定。确认目标、范围、验收标准、ticket 状态和依赖；按需检查相关代码、接口、配置和已有测试，找到会影响实施顺序或方案的事实。记录来源及可定位的版本、路径或标识，区分已有事实、推断和待确认事项。

核对来源的范围、行为、接口和依赖是否一致。发现缺失、冲突或循环依赖时说明涉及的来源、影响及待解决的问题，不把推测写成既定决策；继续规划不受影响的部分。缺少某类输入时先查找相关材料，仍缺失则说明覆盖限制，针对现有依据完成可行部分；只有影响实际推进的关键决策才提出具体问题。

## 制定计划

面向 AI 编码代理编排任务，同时让人能检查和接手。以交付结果为单位组织阶段或步骤，保留 ticket 标识并按真实依赖排序。每一步写清目标、输入、涉及的模块或已核实的文件与接口、执行动作、前置条件、交付物、完成标志及验证方式。为有依赖关系的任务明确上游交付物或接口约定。计划粒度以执行者能据此推进和检查为准，不虚构精确文件、命令、工期或人员安排。

按项目需要编排准备、实施、验证、集成和完成等环节，写清各环节的进入条件、完成条件和交接信息。默认按依赖顺序串行；用户或仓库允许并行且任务边界清晰、无依赖冲突时，说明可并行任务、各自范围及汇合条件，并在汇合时验证任务间的交互。共享文件或偏好的顺序本身不构成阻塞，也不因 ticket 数量强制使用多代理。

建立简洁的追踪关系，将每项范围内的验收要求和设计行为对应到 ticket、实施步骤与验证方式；明确不适用、未覆盖或被阻塞的条目。避免复制整份详细设计或重新拆写已有 tickets。列出会影响实施的关键风险、兼容性、迁移、上线和回退措施，仅在相关时展开，并说明依赖的外部条件。

验证方案优先覆盖受影响的行为、关键边界和跨步骤集成；从仓库配置确认可用的检查方式。无法确认的命令写成待核实的验证目标，不把计划中的检查写成已执行或通过。根据实际复杂度安排检查点，无需为每个 ticket 强制增加分支、提交或全量测试。

## 执行与状态

让计划同时充当执行记录：复用已有状态记录，为每个任务保留状态、实际验证结果、阻塞及必要的交接信息；新规划的任务标为未开始。每个任务采用一个互斥的当前状态，状态变化时同步更新任务记录和总进度；完成比例按已完成任务数除以任务总数计算，任务范围变化时更新总数并说明原因。要求执行者在验收条件满足、必要验证通过且结果记录后才标记完成；验证无法执行时标为待验证，并记录原因。

要求 agent 每完成一个任务，立即向用户简要说明该任务的结果、实际验证及当前总进度，再继续后续可执行任务；存在未完成或未验证内容时如实说明，不将其报告为完成。汇报不改变用户指定的执行范围或暂停要求。

失败或阻塞时，要求执行者记录原因、影响和恢复条件，修复明确属于当前任务的问题，继续不依赖该阻塞项的工作。需要产品决策或额外权限时提出具体问题；无法安全判断时保留现场。计划只规定这些执行规则，后续由用户选择执行方式，不因生成计划自动开始实施。

## 交付

按用户指定路径保存；否则优先复用相关已有实施计划，在不覆盖无关内容、历史或执行状态的前提下更新，若没有则创建 `docs/<功能名>-implementation-plan.md`。已有计划是代码骨架或其他工作流使用的共享产物时，保留其所需字段和记录；无法安全合并时选择新文件并说明。明确要求仅在对话中交付时不写文件。

文档至少包含来源和范围、实施顺序、需求到步骤及验证的追踪、任务总进度、风险与待确认事项；按需要补充迁移、发布和回退安排。任务总进度应说明任务总数、已完成、进行中、待开始、待验证和阻塞数量，并列出当前完成比例、最近完成项、当前进行项、下一批可执行项及影响整体进度的阻塞。交付前检查所有范围内验收要求均有对应步骤与验证或明确标记缺口，依赖无未解释的循环，阻塞项和假设可辨认。报告文档路径、来源及影响执行的未决问题；后续实现应同时参考原始材料和计划。

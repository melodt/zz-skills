## 1. 背景与问题

现有 `implement` 在可行时使用 `tdd` 并运行检查；`implement-spec` 要求各 ticket 的实现者使用 `tdd`。`tdd` 关注公开接口和逐条红绿循环。这些约定并未要求维护独立的详细用例文档、按文档逐条留证，也没有规定所有范围内用例通过才能结束验证。

第三方 skills 可能随更新覆盖本地改动，需要在自有工作流和目标项目规则中维护测试要求。图片提供了用例字段、正常/边界/异常分类和详细步骤的参考，不提供当前项目的业务规则。

## 2. 目标与非目标

目标：

- 基于至少一类已有 spec、tickets 或功能细节设计，生成可执行、可追溯的功能测试用例并记录覆盖缺口。
- 实现前准备用例；开发中保持其与已确认需求同步；验证时逐条记录结果和证据。
- 提供单项任务和完整 spec 两个自有实现入口，并提供目标项目可采用的 `AGENTS.md` 规则。
- 在当前批准的验证范围内，所有适用用例实际通过后才声明该范围验证完成；未验证范围独立报告。

非目标：修改第三方 skill、强制所有项目默认启用、建设测试管理平台或 CI 门禁、将所有用例都实现为自动化测试、把示例图片中的业务数据当作真实需求。

## 3. 用户与场景

- 需求或测试负责人提供可用文档，希望得到详细用例并发现需求缺口。
- 实现者使用自有入口完成一个 ticket 或完整 spec，依据用例开发、验证和报告。
- 项目维护者把补充规则纳入需要该工作流的项目，覆盖直接调用第三方实现 skill 的情况。

## 4. 方案概述

新增一个负责用例生成和验证的自有 skill，以及两个分别编排单项实现和完整 spec 实现的自有入口。目标项目可采用简短的 `AGENTS.md` 规则引用该工作流。第三方 skills 保持独立安装及更新。

直接修改第三方 skill 的代价是更新时可能丢失规则；只在实现后调用验证 skill 则可能在验证前已经提交、关闭 ticket 或将 PR 标为待评审。本方案要求入口控制完成动作的时序；若现有第三方流程不能配合，按用户批准的约束编排其适用步骤，不能先完成外部动作再补验。

## 5. 详细设计

### 5.1 组件与入口

| 组件 | 职责 | 输入 | 输出 |
|---|---|---|---|
| 测试用例 skill | 生成、更新、执行及汇总用例 | 至少一类来源文档、可选任务范围和环境 | 功能用例文档、逐条执行记录、覆盖及阻塞说明 |
| 单项实现入口 | 编排单个任务的用例、实现和验证 | spec 或 ticket，以及可用详细设计 | 改动、该任务用例结果及完成状态 |
| 完整 spec 实现入口 | 按 ticket 依赖编排实现，汇总跨 ticket 验证 | spec、关联 tickets、可用详细设计 | 集成结果、ticket 与功能范围的用例结果 |
| 项目规则模板 | 让采纳规则的项目在直接调用第三方实现 skill 时也遵守门槛 | 项目维护者选择并纳入规则 | 项目范围内的指令，不提供技术强制能力 |

以上均为设计中的自有组件，名称和安装位置以实现时最终选定的目录及 skill 元数据为准。自有入口可利用第三方流程，但必须确保本文的时序和用户的授权得到执行；不能依赖第三方 skill 更新后仍具备未明确约定的行为。

### 5.2 来源、覆盖与用例

- 明确指定来源时读取全部指定材料；同时查找用户指向的其他可用来源。至少一类来源可用才能生成正式用例；缺失其他类型要在文档中标明。若指定来源不可读取，记录缺失及影响；不能声称已覆盖其内容。
- 分别提取功能、角色、操作、规则、状态和验收标准，建立来源到用例的覆盖关系。ticket 限定任务范围及依赖；详细设计补充已确认的交互与状态；spec 说明整体行为。来源冲突列出双方及影响，不按文档类型自行裁决。
- 按功能维护一份 Markdown 文档，默认沿用项目已有文档目录和命名规则；没有约定时使用 `docs/<功能名>-test-cases.md`。优先更新已有对应文档，不覆盖无关内容。每个独立行为和重要分支均可定位到用例或明确的待确认/不适用说明。
- 依据来源和风险选择正常、边界、异常、权限、状态及跨 ticket 场景；仅在适用时纳入对应类别。不虚构业务规则、界限数值、错误文案或未授权的测试环境。
- 每条用例具有稳定且功能内唯一的编号；更新时保留已有编号，删除或合并时保留可追溯的变更说明。用例至少包含模块、标题、优先级、测试类型、关联来源和适用 ticket、前置条件、环境、测试数据、编号操作步骤和可观察的预期结果。无法确定的数据标记待确认，而不是填写猜测值。优先级服务于排序，不豁免范围内验证。
- 每条用例记录最新执行状态、实际结果、执行时间、执行人或工具、测试版本及可访问的证据位置；生成时这些执行字段为空或标为未执行。证据可为测试报告、命令输出、截图或人工记录，必须能对应当前用例、实际结果和被测版本；不将密码、令牌等秘密写入文档。
- 同一文档维护必要历史：失败、阻塞及其解决或重跑记录需可追溯；重复生成按编号更新，不重复新增同一用例或抹掉已有证据。需求变更影响既有预期时记录来源及变更，标记旧结果需复验。

### 5.3 状态与完成门槛

用例状态为 **待确认、未执行、通过、失败、阻塞、需复验**。用例信息不完整或来源冲突时为待确认；准备完毕但未执行为未执行；真实执行后按观察结果记通过或失败；环境、依赖或授权缺失而不能执行为阻塞。代码、需求、环境或测试数据变更可能使旧证据不再适用，此时标为需复验。失败或阻塞解除后可以重跑并保留历史；仅真实结果符合已确认预期且证据有效时标为通过。

测试执行范围由功能或 ticket、其已确认适用用例和必要集成场景共同确定。只生成或只执行部分用例不能声明完整范围通过。用户明确批准缩小范围时，记录批准后的范围和未纳入内容，仅可声称缩小范围通过，不能声称原完整范围通过。待确认、未执行、失败、阻塞和需复验均不是通过。

优先执行受影响的用例；通过记录仅在被测版本及相关需求、环境、数据和依赖仍适用时复用。不能合理判断影响范围时扩大检查；在隔离的 ticket 验证之外，集成后执行涉及多个 ticket 或集成变化的用例。自动化测试可以提供执行证据，但仅当其确实覆盖用例的条件、步骤和预期；人工或工具操作需同样记录实际结果。

### 5.4 第三方工作流、动作和授权

单项入口在实现前准备用例，再按已有适用规则和用户确认的测试接口逐项实现；完成前验证该任务范围。完整 spec 入口在工作开始时建立全功能用例与 ticket 映射，向各实现者提供来源、用例和任务范围；每个 ticket 在提交前验证自身范围，合并后的集成版本再验证跨 ticket 和受集成影响的用例。

第三方 `implement` 包含提交动作，`implement-spec` 包含集成、可能的 PR 状态变更及 ticket 关闭动作。自有入口和项目规则须使适用范围验证通过后才执行这些完成动作；验证受阻则保留实际状态、报告原因并停止受影响的完成动作。已存在的用户授权、仓库规则和上级指令仍适用；新 skill 不自行授权提交、发布、访问外部环境或关闭工单。目标项目维护者负责安装自有 skills 和纳入规则；不能访问或修改无授权的目标项目。

第三方更新后，维护者需核对其入口、调用方式和完成动作是否仍可与自有约束协调。规则是 Agent 指令而非技术门禁；未安装、未采纳、被更高优先级指令覆盖或未被遵循时无法保证执行。若需要技术强制，应另行设计 CI 或其他门禁，不属于本次范围。

## 6. 功能步骤

| 步骤 | 触发方与输入 | 处理与可观察结果 | 失败收场 |
|---|---|---|---|
| S1 | 用户调用用例 skill 或自有实现入口，并提供功能、来源及可选范围 | 读取可用来源，识别当前功能、ticket 和缺失项 | 无任何可用来源时报告缺失，停止生成正式用例 |
| S2 | 用例 skill 接收来源 | 建立来源、功能、分支及 ticket 覆盖关系，识别冲突 | 对冲突和未知预期标待确认，继续处理无关部分 |
| S3 | 用例 skill 根据覆盖关系写入功能文档 | 创建或更新稳定编号的详细用例和未执行状态，保留历史 | 文档无法写入时报告路径和原因，不宣称已交付 |
| S4 | 用户或实现入口触发实现 | 将相关用例及来源交给实现者；按适用流程和已确认接口增量开发 | 用例或业务决策阻塞时停止受影响实现并报告 |
| S5 | 实现者对当前 ticket 或功能触发验证 | 准备经授权的环境，执行适用用例，记录版本、结果和证据 | 缺环境、权限或依赖记阻塞；实际不符记失败；均不得记通过 |
| S6 | 完整 spec 入口集成已通过的 ticket | 对集成版本执行必要的跨 ticket 和受影响用例，更新证据 | 集成失败或验证未通过时保留记录，停止受影响完成动作 |
| S7 | 入口汇总批准范围 | 所有适用用例通过后，报告范围、证据及未覆盖项，再执行已获授权的完成动作 | 未全部通过时报告未完成、失败/阻塞及下一步，不关闭受影响任务 |
| S8 | 项目维护者为目标项目配置规则 | 安装自有 skills，将项目规则加入适用 `AGENTS.md`，直接调用第三方 skill 时也按 S1–S7 执行 | 未安装或规则不可用时报告无法保证门槛；不改第三方安装目录 |

只请求生成用例时执行 S1–S3 并报告“用例已生成、尚未验证”，不隐含授权实现或执行外部操作。只请求验证时读取现有用例，按 S5–S7 执行，不隐含授权修改生产环境或关闭任务。

## 7. 边界与异常

- 来源缺失或不一致：记录来源、缺项、冲突及影响；只有不受影响且有依据的预期可进入可执行状态。
- 一个 ticket 依赖其他 ticket 或环境：未满足条件的用例记阻塞；各自通过不能替代集成验证。
- 结果部分通过：汇总通过与未通过的编号，不能把未执行自动转为通过；用户明确缩小范围时仍需报告排除项。
- 测试运行失败或证据缺失：区分产品不符合预期和测试环境阻塞；没有有效证据的用例不能标为通过。
- 需求、实现或环境变化：评估既有结果是否仍适用，影响不明则扩大复验范围。
- 重复生成或多人更新：保留稳定编号、历史及他人记录；发现并发冲突先合并或报告，不静默覆盖。
- 外部系统或敏感信息：仅使用已授权环境和数据，避免在记录中泄露凭据；权限不足时标阻塞。
- 第三方流程要求先做完成动作：自有入口遵循用户确认的门槛；无法协调时暂停相关动作并说明冲突。

## 8. 验收标准

1. 给定任意一类可读取的来源，生成文档列出已读取和缺失来源，并为范围内已确认行为建立可追溯用例；三类均不可读取时不生成声称完整的正式用例。
2. 给定互相冲突的预期，文档展示冲突双方、影响和待确认状态；不选择一方伪装成事实，其他不受影响的用例仍可生成。
3. 一条详细用例包含 5.2 节规定的字段，步骤与预期能够独立执行和判定；生成后执行记录为空或未执行。
4. 重复生成或需求更新时，未变化的用例保留编号及历史，受影响用例记录来源变更并要求重新评估旧结果。
5. 用例失败、待确认、未执行、阻塞或需复验时，该用例不被记为通过，所属批准范围不被声明验证完成。
6. 用户明确批准缩小范围时，报告新范围及排除项；仅新范围内全部适用用例通过才可声明该范围完成，不能将其表述为原范围全通过。
7. ticket 验证通过不替代集成验证；集成后的跨 ticket 和受影响用例完成后才能声明完整 spec 范围通过。
8. 能证明用例条件和预期的自动化结果可作为证据；不能证明用例的单一测试通过不能替代对该用例的验证。
9. 对被测版本或相关条件变更的结果进行影响评估；失效证据标为需复验，影响不明时扩大验证。
10. 在门槛未满足时，自有入口不执行受影响的提交、关闭 ticket 或 PR 待评审动作，并清晰报告阻塞；有授权且门槛满足后按适用流程执行。
11. 目标项目采纳规则后，可直接调用第三方实现 skill 并按约定遵循门槛；未采纳规则的项目不被声称已经受其约束。
12. 测试记录不包含实际凭据；无权限访问环境时记录阻塞，不将缺失执行替换为推测结果。

## 10. 风险、假设、开放问题

| 类型 | 内容 | 影响与处理 |
|---|---|---|
| 风险 | 第三方 skill 更新后流程或完成动作变化 | 每次适配时核对其最新指令；不能协调时停止受影响的完成动作。 |
| 风险 | 指令遵循不能保证技术强制 | 如需不可绕过的门槛，单独设计 CI 或其他自动化控制。 |
| 假设 | 用户接受 Markdown 作为默认载体，且项目已有约定优先 | 若目标项目有其他测试管理系统，需另行确定同步方式。 |
| 假设 | 用例按可确认的需求和风险确定，不把所有潜在测试类型当成范围内需求 | 需求负责人可明确扩展验证范围；无法确定的预期保持待确认。 |
| 开放问题 | 自有 skills 的最终名称由实现时按仓库现有命名风格选定 | 不影响当前流程和验收；若需与已有 skill 名称兼容，由维护者确定。 |

## 1. 背景与问题

仓库已有 `spec`、tickets 和详细设计之后，仍需要一轮重复的结构化工作：确认输入范围、映射模块和文件、搭建接口与类型、接通最小入口、留下可追踪的占位点，并验证生成结果能被项目工具链识别。现有实现型 skill 偏向直接完成业务逻辑，无法稳定表达“先完成代码骨架，再交给后续 ticket 补齐行为”的边界。

`code-skeleton` 用于把已确认的设计输入转化为可编译、可验证、可继续实现的代码骨架，同时保护人工代码、保留设计缺口，并让每个变更可追溯到 ticket。

## 2. 目标与非目标

**目标**：

- 从仓库和用户指定位置发现并读取 `spec`、tickets、详细设计、`AGENTS.md`、配置和相关代码。
- 建立“文档条目 → ticket → 模块 → 文件 → 验证”的追踪关系。
- 按依赖顺序生成公共接口、类型、模块边界、适配器、最小实现、入口接线和测试骨架。
- 使用可搜索的 `TODO(ticket:<id>, kind:<category>)` 标记剩余工作。
- 生成计划、manifest、验证结果和可恢复的运行记录。
- 在不覆盖人工实现的前提下支持重复运行、局部失败和增量补齐。

**非目标**：

- 不替代需求分析、详细设计或 ticket 拆分。
- 不猜测缺失的公共契约，不自动关闭 ticket。
- 不自动 commit、push、建分支、访问生产系统、执行真实迁移或读取真实凭据。
- 不因“生成骨架”而擅自引入框架、重构无关模块或扩大 ticket 范围。

## 3. 用户与场景

| 角色 | 诉求 | 关键约束 |
|---|---|---|
| 开发者 | 根据已确认的设计快速建立实现边界 | 保留人工修改，可继续交给后续实现 ticket |
| 评审者 | 在写入前查看范围、映射和风险 | 需要可解释的计划和 diff 摘要 |
| CI / 自动化 | 检查输入映射、占位点和验证结果 | 只能执行 `plan` / `verify`，不能自动 `apply` |

主路径：

1. 开发者指定 ticket 或文档，skill 发现输入并生成 plan，展示待创建、修改、跳过和阻塞项。
2. 开发者显式执行 `apply`，skill 按依赖顺序以 ticket 为事务边界写入骨架并运行分层验证。
3. skill 输出 Markdown 报告和 JSON 结果，记录完成的骨架、TODO、验证证据和后续 ticket。

## 4. 方案概述

**推荐方案：** 一个用户显式调用的 `code-skeleton` skill，采用“发现 → 映射 → 计划 → 分 ticket 应用 → 验证 → 报告”的固定主流程；复杂参考资料和模板放入 `references/`，仓库特定规则通过可选 `.code-skeleton.yml` 覆盖。

**为什么选它：** 入口集中，能把需求解释、代码生成和验证分开；默认先 plan 可以降低误写风险，按 ticket 的事务边界和 manifest 支持恢复与幂等。

**备选：**

| 方案 | 做法 | 优点 | 代价 | 何时选 |
|---|---|---|---|---|
| A（推荐） | Skill 指令 + 参考模板 + 可选仓库配置 | 适配多语言仓库，维护成本低 | 复杂生成依赖 agent 判断 | 设计变化快、项目差异大 |
| B | 固定脚本生成器 | 结果更确定 | 需要维护多语言模板和解析器 | 输入格式和技术栈高度统一 |

## 5. 详细设计

### 5.1 输入发现与优先级

固定顺序：

1. 读取适用的 `AGENTS.md` 和仓库约定。
2. 读取用户显式指定的 `spec`、设计、ticket 文件。
3. 扫描常见目录中的 `spec`、`tickets`、`design`、`docs` 文件。
4. 使用 CodeGraph / codebase-memory-mcp 理解符号、调用关系和影响范围；图谱不可用或不足时再读取具体文件和配置。

优先级：当前用户指令 > 详细设计 > ticket 验收标准 > spec > 现有代码约定。现有代码约定用于补全未规定的实现细节。

默认只处理用户指定 ticket；未指定时先展示发现到的未完成 ticket 并等待选择。

### 5.2 模式与调用

- `plan`：默认模式，只生成计划、追踪矩阵、冲突和预期 diff 摘要。
- `apply`：在用户明确要求执行或传入 `--apply` 后，按计划写入工作区。
- `verify`：只执行已选验证层级并更新结果。
- 支持自然语言调用和 `--spec`、`--design`、`--tickets`、`--ticket`、`--plan`、`--dry-run`、`--apply`、`--verify` 参数。
- 用户参数 > `.code-skeleton.yml` > 仓库自动检测 > skill 默认值。

### 5.3 追踪与持久化产物

- `docs/implementation-plan.md`：人读的计划、追踪矩阵和运行历史。
- `.code-skeleton/manifest.json`：文件、ticket、输入哈希、skill 版本、生成时间和状态。
- `.code-skeleton/runs/<run_id>.json`：单次运行的结构化结果、验证和失败原因。
- `.code-skeleton/tmp/`：生成和语法检查的临时产物；成功后清理，失败时保留。

文档版本以内容哈希为默认标识；若文档有显式版本则同时记录。日志和报告自动脱敏密钥、令牌、连接串及不必要的个人信息。

### 5.4 生成顺序与边界

按 ticket 依赖做拓扑排序。共享公共接口、同一模块或共享文件的 ticket 串行处理；独立 ticket 可并行分析，但应用顺序仍由依赖决定。

单 ticket 的生成顺序：公共接口与类型 → 模块边界 → 适配器和依赖 → 最小实现 → 入口注册 → 测试骨架。

写入前生成到临时目录并做语法级检查；应用失败时恢复当前 ticket 的工作区变更，保留前面已验证的 ticket。目标文件已有人工实现时，按哈希或 diff 检测并只做局部补丁；无法可靠合并则跳过并阻塞。

### 5.5 适配与外部依赖

优先读取 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml`、`Cargo.toml` 等项目配置识别语言和工具链。多语言 ticket 可组合多个适配器。

适配器只负责文件布局、接口写法、占位实现和验证命令，不改变 ticket 范围、需求解释或冲突优先级。

数据库、消息队列和第三方 API 只生成接口、模型、迁移草稿、mock、本地替身和配置样例；真实迁移、真实凭据、认证、重试和限流等未决行为通过 TODO 或阻塞项记录。

### 5.6 占位点与入口

统一格式：`TODO(ticket:<id>, kind:<category>): <remaining work>`。

允许的 `kind`：`business-logic`、`integration`、`validation`、`design-gap`、`manual-decision`。公共接口缺失时不生成猜测性的公开契约；可安全隔离的内部占位可以继续，否则阻塞 ticket。

路由、容器、插件或 CLI 注册属于骨架的一部分，但只有设计或现有注册模式明确支持时才自动修改注册表。

### 5.7 验证与结果

验证层级：`syntax`、`unit`、`build`、`integration`。先运行受影响范围内的最低必要层级，再按失败和影响扩大。每条命令记录来源、超时、输出摘要和状态；外部环境不可用时明确列出未执行的集成验证。

结果状态：`success`、`partial`、`blocked`、`failed`。只有目标 ticket 的骨架完成、阻塞项已记录、验证结果已归档且 diff 可解释时才报告 `success`。

### 5.8 配置

可选 `.code-skeleton.yml` 支持文档目录、ticket 格式、验证命令、语言适配器、TODO 类别和输出路径。配置只覆盖 skill 的机械规则，不覆盖需求优先级、安全边界或用户当前指令。

## 6. 功能步骤

| 步骤 | 触发方 | 动作 | 输入 | 处理 | 成功结果 | 失败怎么收场 |
|---|---|---|---|---|---|---|
| S1 | 开发者 / CI | 调用 `code-skeleton` | 文档路径、ticket、模式参数 | 读取约定并发现输入 | 输入清单和缺失项 | 关键契约缺失则阻塞，非关键缺失记录假设 |
| S2 | skill | 建立追踪矩阵 | spec、设计、tickets、代码结构 | 映射需求、模块、文件、验证 | 无遗漏或明确设计缺口 | 冲突列入阻塞项，不猜测 |
| S3 | skill | 生成 plan | 追踪矩阵、配置、依赖 | 排序 ticket，计算预期文件变更 | `implementation-plan.md` 和 diff 摘要 | 目标不明确则停在 plan |
| S4 | 开发者 | 显式执行 `apply` | 已确认 plan | 按 ticket 临时生成、检查、应用 | 骨架写入并更新 manifest | 当前 ticket 回滚，保留前序结果 |
| S5 | skill / CI | 执行验证 | 项目脚本和验证层级 | 运行命令并分类结果 | 结构化验证证据 | 标记 `partial` / `failed`，不掩盖失败 |
| S6 | skill | 生成报告 | 运行记录、diff、验证结果 | 脱敏并汇总 | Markdown + JSON 报告 | 保留诊断产物和恢复上下文 |

## 7. 边界与异常

- 文档冲突：列出冲突双方、影响和待决策项，阻塞受影响 ticket。
- 公共接口不完整：不公开猜测；生成内部占位或阻塞。
- 发现循环依赖：无法拓扑排序时阻塞相关 ticket。
- 目标文件被人工修改：保护现有内容，生成局部补丁或人工合并项。
- 验证命令不存在：执行可用的静态检查和编译检查，报告未执行项。
- 外部服务不可用：使用本地替身，明确未完成的集成验证。
- 变量未解析、语法检查失败或临时应用失败：停止当前 ticket，保留诊断文件。

## 8. 验收标准

- Given 指定了 spec、设计和 ticket，When 执行 `plan`，Then 生成输入清单、追踪矩阵、依赖顺序、文件变更和验证命令。
- Given ticket 的公共契约完整，When 执行 `apply`，Then 生成可被项目工具链识别的接口、类型、模块边界和最小实现。
- Given ticket 仍有业务逻辑未完成，When 查看代码和报告，Then 每个占位点都符合 `TODO(ticket:<id>, kind:<category>)` 格式并可追溯。
- Given 目标文件已有人工实现，When 重复执行同一 run，Then 不覆盖人工代码，并报告跳过或局部补丁。
- Given 某个 ticket 写入失败，When 运行结束，Then 当前 ticket 的变更可恢复，前序已验证 ticket 保留，结果为 `partial` 或 `blocked`。
- Given CI 运行 `verify`，When 存在未映射需求、未解析变量或阻塞项，Then 返回非零状态且不自动写入工作区。
- Given 外部数据库或 API 不可用，When 执行本地验证，Then 使用替身完成可行检查，并明确集成验证未执行。
- 反例：skill 不得因缺少公共接口细节而生成未经确认的公开参数、返回值或错误模型。

## 9. 自评估操作步骤

| 编号 | 评估什么 | 前置 | 操作 | 期望 | 失败信号 | 实际结果 |
|---|---|---|---|---|---|---|
| E1 | 主路径 | fixture 含一个完整 ticket 和可运行验证命令 | 执行 S1–S6 | 生成 plan、骨架、manifest 和报告 | 缺少映射或无法完成 syntax 验证 | |
| E2 | 人工修改保护 | fixture 目标文件含人工代码 | 重复执行 S3–S6 | 文件未被覆盖，报告含冲突或跳过原因 | 人工代码丢失或 manifest 不一致 | |
| E3 | 最危险异常 | fixture 含公共接口冲突和外部依赖 | 执行 S1–S5 | ticket 被阻塞，真实外部系统未被访问，诊断产物保留 | 生成猜测性公开契约或静默连接外部系统 | |

自评估：已按文档推演三条路径，设计逻辑可走通；尚未执行 fixture 或真实项目验证。

## 10. 风险、假设、开放问题

| 类型 | 内容 | 影响 | 谁来拍板 |
|---|---|---|---|
| 假设 | 仓库通常已有可识别的格式化、类型检查、构建或测试入口 | 无入口时只能做有限静态检查 | 项目维护者 |
| 风险 | 多语言和非标准目录会增加适配判断 | 计划可能需要人工修正 | skill 使用者 |
| 风险 | 图谱索引可能滞后于最新写入 | 结构分析需回退到文件读取 | skill 执行者 |
| 开放问题 | 是否为特定团队增加固定 ticket 解析器 | 影响后续脚本化程度，不阻塞通用 skill | 团队维护者 |
